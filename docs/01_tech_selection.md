# 技術選型分析 — 引擎與後端框架推薦

## 1. 需求權衡

本專案的核心約束：

1. **伺服器權威 (Server-Side Authority)**：所有位置、傷害、命中判定、經濟、Spike 皆由伺服器計算，客戶端只上送淨輸入 → 天然防作弊。
2. **128 Hz 高 Tickrate**：固定時間步模擬，需要高性能且**確定性**（可重播、可測試、可回滾）。
3. **完整機制保真**：後座力圖案、彈道、經濟公式等必須「可數值化、可單元測試」。
4. **開源**：License 友善。
5. **可迭代**：我們要在無頭環境（無 GPU）中開發、測試全部邏輯。

## 2. 結論（推薦策略）

> **「引擎無關的純邏輯核心」先行，渲染層後置。**
>
> - **邏輯核心（本專案現在就在做的）**：Python 3.11+ 純函式模組，零外部依賴。
>   所有機制（移動/彈道/後座力/經濟/Spike/技能）以確定性模擬寫在 `server/core/`，
>   用 pytest 驗證。**這層與引擎完全無關，日後可嵌入任何引擎，或原樣移植到 Rust/C#。**
> - **正式伺服器**：Rust (tokio) 或 C# (.NET 8) headless。Python 原型用於快速驗證數學與規則；
>   效能瓶頸（彈道/視線檢測）profile 後以 Rust 重寫熱路徑。
> - **客戶端（渲染 + 輸入）**：**Godot 4.4+**（MIT 授權、輕量、C#/GDScript、易於自訂
>   CharacterBody3D 做客戶端預測）。此層在邏輯核心完成後再實作。

## 4. 伺服器框架比較

| 項目 | Python asyncio（原型 ✅） | Rust + tokio（正式 ✅） | C# (.NET 8) |
|---|---|---|---|
| 開發速度 | ★★★★★ | ★★ | ★★★★ |
| 128Hz×10 玩家模擬 | 可（純邏輯約 10–30% 單核） | 餘裕極大 | 餘裕大 |
| 確定性 | float64 固定順序可保證 | 強 | 強 |
| 生態（序列化/測試） | pytest 完備 | serde/criterion | xUnit |
| 風險 | GIL 單執行緒（邏輯核心可接受） | 開發慢 | 中 |

**確定性策略**：float64 (IEEE 754)、固定 tick 順序、種子化 RNG（match seed）、
禁止依賴 dict 迭代順序、禁止使用絕對時間。

## 5. 網路架構（M2/M3 實作）

- 傳輸：UDP（非可靠），Client → Server 只送 `MoveInput + 輸入序號 + 時間戳`。
- Server → Client：128 Hz 世界快照（delta 壓縮、位置量化、朝向用最小 3 分量）。
- RTT 估算：EWMA 平滑 + 序列號對齊，用於客戶端預測水平與延遲補償視窗。
- 三兄弟：
  1. **客戶端預測**：本地以相同 MovementController 提前模擬，輸入序號對齊。
  2. **伺服器和解**：快照攜帶伺服器已處理的輸入序號；客戶端發現差異 → 校正並重放。
  3. **Rollback 延遲補償**：伺服器命中判定時，將世界回滾到「射擊者畫面時間」再判定
     （僅用於命中，不回溯移動，與真實遊戲一致）。
- 序列化：原型用 msgpack（純 Python），正式版換 Cap'n Proto / FlatBuffers。
- 防作弊：伺服器驗證輸入合法（速度上限、射速上限、擊殺計時），不信任任何客戶端狀態。

## 6. 測試策略

| 層級 | 工具 | 用途 |
|---|---|---|
| 單元測試 | pytest | 每個模組（本次 M1 已建立 20+ 測試） |
| 黃金資料 | 序列化確定性模擬輸出 | 防回歸 |
| 屬性測試 | hypothesis | 隨機輸入下不變量（不超速、不穿透地面等） |
| 整合測試 | 自寫 harness | 10 玩家 128Hz 模擬 5 分鐘無狀態發散 |

## 7. 風險與取捨

- **Python 效能**：純邏輯 128Hz 可行但天花板低；正式版移植 Rust。介面已隔離在
  `server/core`，移植成本低。
- **機制數值不精確**：Riot 未公開數值，所有常數集中為 config，可後續校正。
- **渲染層後置**：前期無畫面，以「可視化測試輸出」（軌跡/圖案 JSON）代替。
